Deploying the Lease Manager

A start-to-finish path from a bare Ubuntu 24.04 VPS to a running, backed-up, HTTPS lease-management app: hardened SSH, a dedicated service account, systemd for the API, Nginx for TLS and static hosting, and both the internal and off-site backup jobs the project brief calls for.

Node.js 22 LTS Express + SQLite (better-sqlite3) React + Vite static build systemd · Nginx · Let's Encrypt
BrowserStaff in China, owner in the US
→
Nginx :443TLS termination/etc/nginx/sites-available/lcm
→
Static filesthe built React app/opt/lcm/app/web/dist
Node :4000loopback only, proxied at /api/*systemd unit: lcm.service
→
Local diskSQLite + uploaded documents/opt/lcm/{data,documents}
⏱ cron inside the app writes a nightly snapshot to /opt/lcm/backups
🔁 certbot renews the TLS certificate automatically
🛡 ufw only ever opens SSH, 80, and 443
Run the app as

Steps below adjust to match — §3, the systemd unit, and every sudo -u lcm command change accordingly. This choice doesn't affect §1: whether you SSH in as root or a sudo user is a separate decision, already covered there.

Prerequisites

  • An Ubuntu 24.04 LTS VPS with root (or sudo) SSH access.
  • A domain or subdomain whose DNS A record already points at the VPS's public IP — check with dig +short lease.yourcompany.com before starting §10.
  • The app's git repository URL, and a way to authenticate to it (a personal access token for HTTPS, or an SSH deploy key).
  • About 20–30 minutes; most of it is apt waiting on you.
📌
Placeholders used throughout

Swap these for your own everywhere they appear: domain lease.yourcompany.com, deploy root /opt/lcm, service account lcm (dedicated-account variant only), systemd unit lcm.service, sudo login deploy.

01

Harden the server

Start as root over SSH and create a sudo user you'll actually work as — don't run the app, or the rest of this guide, as root.

root · first login
adduser deploy
usermod -aG sudo deploy
rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy
⚠️
Before you disable anything

Open a second terminal now and confirm ssh deploy@your-vps-ip logs in with your key. Keep your original root session open until that succeeds — it's your recovery line if a step below goes wrong.

Once the second session confirms key-based login as deploy works, continue there for everything else in this guide.

deploy · sudo
sudo apt update && sudo apt full-upgrade -y
sudo apt install -y ufw fail2ban unattended-upgrades
sudo dpkg-reconfigure -f noninteractive unattended-upgrades
sudo ufw allow OpenSSH
sudo ufw enable

Turn off root login and password auth over SSH — key-only from here on:

/etc/ssh/sshd_config.d/60-hardening.conf
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
deploy · sudo
sudo systemctl restart ssh
⛔
Don't close your root session yet

Open a third terminal and confirm ssh deploy@your-vps-ip still works, and that ssh root@your-vps-ip is now refused. Only then close the original root session.

ufw only allows SSH for now — ports 80/443 open in §9 once Nginx exists.

02

Install Node.js 22

The app was built and tested against Node 22 LTS. Ubuntu 24.04's own apt repository ships an older Node, so use NodeSource's:

deploy · sudo
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs git build-essential python3
node -v   # v22.x
npm -v

build-essential and python3 are a safety net: the database driver (better-sqlite3) ships prebuilt binaries for standard x64 Ubuntu, but having a compiler toolchain on hand means an install never dead-ends if a prebuilt binary isn't available.

03

Create the app's service account

Create the directory layout

The app runs as its own unprivileged, no-login system user — never as deploy or root.

deploy · sudo
sudo useradd --system --home-dir /opt/lcm --create-home --shell /usr/sbin/nologin lcm
sudo mkdir -p /opt/lcm/{app,data,documents,backups}
sudo chown -R lcm:lcm /opt/lcm
📌
Running as root

No dedicated account to create — the app process, and everything under /opt/lcm, is just owned by root. Every sudo -u lcm command later in this guide becomes a plain sudo command; the systemd unit in §8 runs as User=root.

deploy · sudo
sudo mkdir -p /opt/lcm/{app,data,documents,backups}
PathHolds
/opt/lcm/appThe git checkout — code only. Replaced wholesale on every redeploy.
/opt/lcm/dataThe SQLite database file (app.db). Never touched by git pull.
/opt/lcm/documentsUploaded lease PDFs, floor plans, ID scans — classified ordinary/sensitive by the app itself.
/opt/lcm/backupsNightly snapshot + document manifest (§12).

Keeping data outside app means a redeploy can never accidentally wipe a lease record or an uploaded document.

05

Install dependencies and build

This is an npm-workspaces monorepo (shared / server / web) — one install at the root covers all three.

deploy · sudo
cd /opt/lcm/app
sudo -u lcm npm ci
sudo -u lcm npm run build:shared
sudo -u lcm npm run build:server
sudo -u lcm npm run build:web
deploy · sudo
cd /opt/lcm/app
sudo npm ci
sudo npm run build:shared
sudo npm run build:server
sudo npm run build:web

npm ci installs exactly what package-lock.json pins — the same dependency tree that was tested, not whatever ^-ranges resolve to today. build:server compiles TypeScript to server/dist; build:web produces the static bundle at web/dist that Nginx will serve directly in §9.

💡
If npm ci fails compiling better-sqlite3

Re-check §2's build-essential/python3 install, then re-run npm ci.

08

Run it with systemd

/etc/systemd/system/lcm.service
[Unit]
Description=Lease Contract Management API
After=network.target

[Service]
Type=simple
User=lcm
Group=lcm
WorkingDirectory=/opt/lcm/app/server
EnvironmentFile=/opt/lcm/app/server/.env
ExecStart=/usr/bin/node dist/index.js
Restart=on-failure
RestartSec=5

NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/opt/lcm/data /opt/lcm/documents /opt/lcm/backups

[Install]
WantedBy=multi-user.target
/etc/systemd/system/lcm.service
[Unit]
Description=Lease Contract Management API
After=network.target

[Service]
Type=simple
User=root
WorkingDirectory=/opt/lcm/app/server
EnvironmentFile=/opt/lcm/app/server/.env
ExecStart=/usr/bin/node dist/index.js
Restart=on-failure
RestartSec=5

NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/opt/lcm/data /opt/lcm/documents /opt/lcm/backups

[Install]
WantedBy=multi-user.target

The Protect*/ReadWritePaths lines make the rest of the filesystem read-only to this process — it can only ever write inside the three data directories it actually needs.

The Protect*/ReadWritePaths lines are worth keeping even running as root: they're mount-namespace restrictions, not permission checks, so they still make the rest of the filesystem read-only to this process regardless of which user runs it.

deploy · sudo
sudo systemctl daemon-reload
sudo systemctl enable --now lcm.service
sudo systemctl status lcm.service
curl http://127.0.0.1:4000/api/health

Expect {"ok":true}. Tail logs any time with sudo journalctl -u lcm.service -f.

09

Nginx: static files + API proxy

deploy · sudo
sudo apt install -y nginx
/etc/nginx/sites-available/lcm
server {
    listen 80;
    listen [::]:80;
    server_name lease.yourcompany.com;

    root /opt/lcm/app/web/dist;
    index index.html;

    # Slightly above the app's own 50MB document-upload limit —
    # set this lower and uploads fail with a confusing 413.
    client_max_body_size 60m;

    location /api/ {
        proxy_pass http://127.0.0.1:4000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        try_files $uri /index.html;
    }
}
deploy · sudo
sudo ln -s /etc/nginx/sites-available/lcm /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t
sudo systemctl reload nginx
sudo ufw allow 'Nginx Full'

Visit http://lease.yourcompany.com — the app should load over plain HTTP. That's expected; TLS is next.

10

TLS with Let's Encrypt

deploy · sudo
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d lease.yourcompany.com

Answer the prompts (an email for renewal notices, agree to the terms, choose to redirect HTTP → HTTPS). Certbot edits the Nginx file for you — adding the certificate paths and the redirect — and installs a systemd timer that renews automatically.

deploy · sudo
sudo certbot renew --dry-run
systemctl list-timers | grep certbot
11

Lock down the firewall

deploy · sudo
sudo ufw status verbose

You should see exactly OpenSSH and Nginx Full allowed, default-deny for everything else. Port 4000 should not appear anywhere in that list — Node is only ever reached through Nginx's proxy, and the firewall backs that up regardless of what interface it's bound to.

12

Backups

With ENABLE_BACKUP_SCHEDULE=true (set in §6), the running server itself writes a nightly snapshot — a consistent SQLite copy plus a manifest of every referenced document — to BACKUP_DIR at 02:15 Asia/Shanghai time, regardless of the VPS's own system clock. Verify it once by hand:

deploy · sudo
cd /opt/lcm/app/server
sudo -u lcm npm run backup
ls /opt/lcm/backups
deploy · sudo
cd /opt/lcm/app/server
sudo npm run backup
ls /opt/lcm/backups

Off-site copy (required before real data goes in)

The project brief calls for an encrypted, off-site copy — separate from this VPS and outside China. rclone with a crypt remote works with almost any storage provider:

deploy · sudo
sudo apt install -y rclone
rclone config   # create a remote for your chosen storage, then a
                # second 'crypt' remote wrapping it for encryption

Then sync nightly, shortly after the app's own 02:15 job finishes:

crontab -e (as root or a backup user)
0 3 * * * rclone sync /opt/lcm/backups myremote-crypt:lcm-backups --min-age 30m
🗓️
Retention isn't automatic yet

The app doesn't prune old backup folders on its own. The brief's suggested policy is 30 daily copies plus 12 month-end copies — a simple starting cron for the daily part:

0 4 * * * find /opt/lcm/backups -maxdepth 1 -mtime +30 -exec rm -rf {} \;

Exclude month-end folders from that if you want to keep the 12-month-end tier — a manual step for now.

🖥️
The script is a menu once it's installed

Run sudo bash vps-deploy.sh interactively on a server that already has the app installed and you get a menu instead of an unattended redeploy:

1) Change the domain and get a new TLS certificate
2) Check for updates and pull the latest build
3) Reinstall everything with current settings
4) Change the admin login email
5) Reset a user's password
6) Show service status
7) Exit

Option 2 is the routine "is there anything new" check: it fetches, shows you the commits you're missing, and only pulls/rebuilds/migrates/restarts if you say yes.

Option 1 actually migrates the site to a new domain — rewrites the Nginx config, requests a fresh Let's Encrypt certificate for it, and updates WEB_ORIGIN. It warns (but still lets you proceed) if the new domain's DNS doesn't yet resolve to this server, since the certificate request will fail until it does. The old certificate is left in place unused; the script prints the certbot delete --cert-name command to remove it once you're sure you don't need it.

Option 3 is today's full deploy flow, safe to re-run any time — everything it touches is skipped if already configured.

Each menu item is also a direct flag for cron/automation, e.g. sudo bash vps-deploy.sh --check-update -y or --change-domain, --change-admin-email, --reset-admin-password, --status. A non-interactive caller (no TTY — cron, CI) with no flag at all keeps the original unattended behavior: a full reinstall using whatever domain/admin email are already on file.

Troubleshooting

SymptomLikely cause & fix
Nginx shows 502 Bad Gatewaylcm.service isn't running. Check sudo systemctl status lcm.service and sudo journalctl -u lcm.service -e.
curl 127.0.0.1:4000/api/health refuses the connectionCheck PORT in .env matches the port in Nginx's proxy_pass; check what's actually listening with ss -tlnp | grep 4000.
Document upload fails with 413client_max_body_size in the Nginx site file is lower than the app's own upload limit — raise it (§9 uses 60m).
Build fails: Cannot find module '@lcm/shared'Run npm run build:shared before building server/web — the workspace scripts self-heal this automatically as of the current codebase, but a very old checkout may not have that fix.
Certbot fails the HTTP-01 challengeEither the DNS A record isn't pointed at this VPS yet, or ufw isn't allowing port 80 — confirm §9's ufw allow 'Nginx Full' ran.
better-sqlite3 fails to buildsudo apt install -y build-essential python3, then re-run npm ci.
Locked out of SSH after hardeningUse your VPS provider's web/VNC console to log in as root and revert /etc/ssh/sshd_config.d/60-hardening.conf.
